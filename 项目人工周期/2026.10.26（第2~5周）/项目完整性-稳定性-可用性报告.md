## 四、稳定性

### 4.1 设计机制

| 机制 | 作用 |
|---|---|
| 状态机 + CAS | 所有流转带 `WHERE status=expected`，并发下只有一个 worker 成功 |
| Redis ZSet 队列 | 优先级 + FIFO；出队后二次校验状态，跳过残留元素 |
| 配额原子扣减 | `used_count+1 WHERE used_count<limit`，失败回滚 |
| 重试上限 | 默认 3 次，失败清理旧产物 |
| 失败清理 | 半成品与孤儿产物自动删除 |
| 可选引擎降级 | 健康检查失败只影响对应能力，不拖垮整体 |
| 限流 | 登录/注册/上传/建任务按 IP/用户计数，Redis 故障时放行 |
| 下载令牌 | 绑定用户+产物，Redis SETNX 一次性消费，fail-closed |
| 调度器容错 | 队列轮询异常记录告警，不中断定时任务 |
| 线程上下文清理 | JWT 过滤器 finally 清理 ThreadLocal，避免身份串号 |

### 4.4 运行期发现并修复的缺陷

1. `.dockerignore` 排除构建产物 → 白名单 jar。
2. MySQL/Redis 宿主机端口与 Windows 保留段冲突 → 移除宿主机映射。
3. `SecurityConfig` 与 `RateLimitFilter` 循环依赖 → 拆分 `RedisConfig`。
4. Spring Boot 3 Redis 前缀错误 → `spring.data.redis`。
5. 能力目录未判断引擎健康 → 可用性 = 支持 + 健康检查。
6. 队列轮询异常刷栈 → 捕获并告警。

> 这 6 项均为真实运行期问题，单元测试无法发现；通过 Compose 冒烟暴露并修复，说明“端到端验证”不可替代。

## 五、可用性

### 5.1 部署与访问

- `docker compose up -d --build` 一键启动；数据卷持久化 MySQL/Redis/文件。
- 前端 `http://localhost/`；API `http://localhost:8080/api`；接口文档 `/api/doc.html`。
- 前端通过 Nginx `/api` 反向代理，跨域与路径问题已在部署层解决。
- MySQL/Redis 不暴露宿主机端口，减少攻击面与端口冲突。

### 5.2 交互与引导

- 用户端：拖拽上传、格式推荐、参数表单、任务状态与诊断、下载、反馈、AI 助手。
- 管理端：统计卡、筛选、回复、状态修改；运维端：引擎/队列/存储。
- 能力目录返回参数 Schema 与 `available`，前端可置灰不可用格式。
- 错误码语义化（1001 配额、1002 大小、1003 格式、1006 下载、1011 限流）。
- 首发用户即管理员，便于课程演示与初始化。

### 5.3 可维护性

- 六类 SPI（引擎/质检/存储/队列/AI/通知），替换实现不改业务主链。
- 引擎健康检查与能力目录一致；可选引擎缺失有明确提示。
- README 覆盖 Docker/本地启动、配置项、格式矩阵、测试命令。
- 冒烟脚本可复现，适合答辩前回归。

### 5.4 已知限制

| 限制 | 影响 | 建议 |
|---|---|---|
| CAJ/DjVu/Pages/OCR 依赖外部工具 | 相关能力显示不可用 | 演示时说明“按设计降级”；需要时在镜像中安装 |
| MinIO 仍为占位 | 仅本地存储 | 后续接入对象存储 |
| 无 Flyway | 数据库变更需手工执行 | 后续引入迁移工具 |
| 无 CI/CD | 依赖本地构建 | 后续补 GitHub Actions |
| 实时进度为轮询 | 秒级延迟 | 可升级 SSE/WebSocket |
| 问卷真实数据未回收 | 需求分析缺定量数据 | 汇报前补充样本与占比 |
